Case Study · Client A — Industrial Services Group

Nexus Internal
Finance Suite

One LAN-hosted command center for the finance team of an Egyptian industrial-services group: ETA e-invoice reconciliation, VAT (Form 10), procure-to-pay traceability, NL↔EG intercompany transfers and landed costs — running read-only against a live Odoo 17 Enterprise instance.

My role: sole finance-ops engineer + AP analyst Stack: Python stdlib · XML-RPC · SQLite · vanilla JS Timeline: Aug–Nov 2026 · iterative releases Users: AP & finance team (LAN)

The problem

The Odoo instance existed, but the procure-to-pay process largely lived outside it: RFQs and POs were created on paper and entered late (or never), no 3-way matching stood between an invoice and a payment, project/analytic allocation was missing on most purchase lines, and incoming Egyptian Tax Authority (ETA) e-invoices were checked by downloading portal exports by hand. Duplicate payments, missed invoices and penalty exposure were all live risks.

Context & constraints

  • Odoo 17 Enterprise, Odoo Online (SaaS) — custom Python modules are not installable, so all automation had to live outside Odoo and work read-only over XML-RPC/JSON-RPC.
  • Egyptian ETA portal has no usable push feed for suppliers — incoming e-invoices can only be pulled with an authorized ERP registration; portal data had to be treated as the source of truth for what was actually posted.
  • Hard confidentiality rules (business rules written for the team): outputs in English, Arabic only for UI text; read-only against production; every correction gated by explicit approval.

No framework, no build step, no cloud dependency: a single Python server serves the SPA, the APIs and the SQLite reads. Authentication is enforced with HttpOnly cookies, per-user tab permissions, a 72-hour read-only kill-switch and a hash-chained audit log. Unknown POSTs are denied by default.

Modules shipped (12)

  1. VAT Return · Form 10 — sales/purchase books assembled from Odoo, XML-rate aware, Excel export for the tax preparer.
  2. Invoice Control Tower — ETA portal incoming e-invoices matched against Odoo vendor bills; 18-status model (matched / reference-mismatch / missing on portal / ETA rejected / ETA cancelled…).
  3. AP × ETA Reconciliation — legacy matching path kept live beside the Control Tower.
  4. P2P Control Tower — Bill → PO → Receipt traceability with PO-line analytic (project) allocation coverage.
  5. Bank & Treasury — treasury/bank expense analysis with withholding-tax flags.
  6. ETA Portal connect — OAuth2 token flow for live portal pulls.
  7. RFQ Builder — parses PDF invoices and drafts RFQs/bills.
  8. Branch Sync — NL→EG cross-company stock transfer engine (dry-run default; landed-cost split).
  9. Landed Cost — true import cost (goods + freight + duty) allocated to stock valuations; Form-4 driven.
  10. Cash Outflow — supplier-voucher and stock-expense analysis, FX-aware.
  11. Nexus Transfer — live dashboard for the NL→EG intercompany transfer program.
  12. Admin / Users — user vault, roles, audit review, backup, read-only switch.

Controls designed and enforced through the suite and SOP:

  • Mandatory RFQ → PO in Odoo before payment — no PO, no payment.
  • Project-linked POs — customer + project number mandatory (root-caused via the P2P discovery: PR↔PO linkage was effectively zero and PO-line analytic coverage was low; the deck to senior management proposed exactly these fixes).
  • Three-way match gate — invoice vs PO vs receipt before any payment run.
  • Duplicate-invoice detection — normalized references catch near-identical IDs (including invisible Arabic diacritics).
  • Monthly vendor statement reconciliation — supplier ledgers verified against statements; disputes resolved before payment.
  • Aging visibility — current / 31–60 / 61–90 / 90+ buckets pushed weekly to the AP team.

Challenges → solutions

  • Invisible Arabic diacritics in ETA references silently broke legacy exact matching → normalization pipeline (NFKC, zero-width strip, harakat removal, casefold) + O(n) indexed exact match with containment diagnostics.
  • Legacy tool returned false “MATCHED” verdicts → deterministic 18-status model, completeness guard, supplier-risk weighting, and re-verdict of questionable legacy matches. Re-lookup went from 22.9s per click to 74–670ms, with a one-shot sync replacing repeated clicks entirely.
  • Live-system safety → every write gated: dry-run default, DRAFT-only landed costs, before/after money snapshot with drift abort, and an audit row per applied change.
  • Multi-entity transfer drift (NL→EG) → manifest-driven bot, per-item reconciliation, mirror JEs on interim clearing accounts; no customer-facing invoices between branches.
  • No source-controlled history → change-control via dated build-log docs, route→permission maps, and snapshot backups before every merge.

Results (approved figures only)

30–300×faster e-invoice lookups (22.9s → 74–670ms)
30–40 unit tests for the matching engine (fixtures only, no live system)
208k EGPcorrection posted in a 49-item phantom-stock pilot
96.8M EGPphantom stock diagnosed across ~935 local items

Beyond the numbers: a production sync surfaced a material backlog of portal-posted e-invoices missing from Odoo — escalated to management with a remediation plan; VAT Form 10 preparation became a repeatable, reviewable process; and the suite became the AP team's daily surface instead of scattered spreadsheets.

Lessons

  1. Fix controls at the source — process discipline beats after-the-fact cleanup.
  2. Read-only first; writes only behind explicit approval with before/after snapshots.
  3. Deterministic, testable engines over “smart” heuristics — especially for tax data.
  4. Ship the small working thing (stdlib + SQLite) — the ambitious Node/React plan stayed a plan.
  5. Audit everything; if it isn't logged, it didn't happen.
